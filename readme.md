反正 ChatGPT 跟我说 Home Assistant 能连纯蓝牙，但讲道理，前面我搞逆向的那些日常电子小垃圾，我还没放到 Home Assistant 上连过。这事先以后再说吧，那些设备目的都很单一、很 specific，其实用不着放到 unified 平台上来。最主要是现在懒得像条狗，而且我亲爱的 Codex 那个 5 小时的 usage limit 限制还没解，还得等着。

回到正题，OpenAI 那边能做到实时对话的（比如 Realtime API），拆开来看输入其实不能说是 realtime video，不然算力直接爆炸了。准确地说是连续的图像帧加上 audio：

1. Audio 这边确实是连续的
2. 图像这边跟其他以图像为输入的模型一样，基本上都是抽帧

不管是现实实现还是成本考虑，抽帧都是最实际的设计。我们又不需要像工业机器人那样按毫秒级来算，作为一个智能小助手，差不多就可以了。

如果这样的话，Home Assistant 那边现有的 LLM Vision 肯定是用不了了，因为那边绝对不支持将 Audio 作为输入。反正这种非常 Customized 的东西我早料到得自己手搓，只能自己写了，这个没办法。

再回头看，在目前还没有真正的 AGI 像神一样降临的阶段，基本上就确定用 ChatGPT Realtime 2.1 来作为 provider。

我们得考虑成本，毕竟 API 算钱我也肉疼：

1. 输出是按照 output token 计费的。
2. 输入的 context window 则是声音加上连续多帧图像。每次有输出或进行推理时，都会把当前收集到的这一串帧和听到的音频塞进 conversation 作为输入。

它那边的视频处理做得很好，会自动过滤掉 silent 状态下的视频，没有声音时不会自动触发推理。但它在图像帧作为输入时，确实没有判断「画面是否有变化」的机制，无法据此过滤是否要塞入 conversation，所以这块必须自己做。

很多摄像头会把 motion detection 作为公开事件暴露出来，可以直接当作 trigger。但讲道理，EBO 这边并没有把 motion detection 作为公开事件暴露出来，所以这里还得自己写、额外加一层自己的逻辑。

我又去改了一下 Prompt。但其实还有个问题：它初始的时候说话很空。我觉得这个倒也不怪模型，完全可以通过人工去调整优化。

我说的“空”是指，它类似于一个 zero-shot 的场景：一开始没有人说话，也没有什么有效输入，用户在没有实质内容的情况下单纯问一句“你在吗？”，它肯定就会回“我在呀，我一直在陪伴你”这种没什么实质内容的话。但我不太喜欢这种回复，我想个办法把它改得更好一些。

因为这里有个逻辑：一般来说，用户要是有具体的事，就会直接跟陪伴助手说，比如问今天天气、查邮件等，这种情况其实不会遇到冷启动问题。但有些场景下用户可能只是单纯觉得 lonely，想找人说话，自己一时又想不出话题，所以才会问“你在不在”
所以这部分肯定得改。我不太确定光靠 Prompt 能不能解决，大概率是可以的。因为即使环境里发出了一些声音，它没从中获取到有效信息，这时候单纯搭话是没问题的；但我很介意它好几次直接说"没看到人"或者"人不在家"。

我还是得去 API platform 上做个实验看看，不然这块确实不好处理.

以及，by the way，人还是要有一点系统思维的。现在它刚好成长到那种我脑子有点不够用的状态了，我自己脑子的 context window 都有点承接不住这个事。

还有个事，刚才我这边 Wi-Fi 断了一下，出了一些问题。我由此想起来，自己在整个 build 的过程中基本都没考虑断网的问题，也完全没跟 Codex 提过。

虽然 Codex 在写代码方面可圈可点，但在工程问题上，考虑到之前很多实际使用场景下它的考虑完全不周到，我觉得在这方面还是得专门去多做些考虑。因为它是真的你不跟它说它就不干。

让 Codex 自己去修吧。他那边有个 Docker 容器是专门去连 EBO Bot 的，他确认了断网之后没办法自动重连，这就会导致视频流断流。视频流一旦断了，我这台设备上后续的一些处理肯定就成不了了，先让他去修。

其实到现在，整个架构就已经进到深水区了。讲道理，从他一开始跟我说搞了三个 Docker container 去实现整件事的时候，就已经进到深水区了。只是那个时候我还没有产生"自己能明白他在做什么、并且能针对我的需求去做 robust 优化"的这种妄想，所以当时没怎么觉得。而且那时候整个流程都没跑下来，可行性都没验证，更谈不上折腾什么框架。

但现在可行性确实验证下来了，整个已经能跑通，我就开始对它的稳定性以及易用性（不费人性）有了更高的要求。

我这边始终是一个单用户的状态，就是我这台设备和我家里那台 EBO Bot。所以整件事确实用不着非得架到云上，真用不着。有在云平台上维持一台 EC2 或者 Windows 实例的经费，我还不如多充点 API token。

跑了几天，我觉得好很多了。成本这方面控制非常之好。

另外就是 noise reduction（降噪）设置，那个开了之后好了非常多，不至于说家里一有什么动静就莫名其妙把这个程序给唤醒了。现在父母那边反映说，它的干扰少了很多

现在的逻辑是：先把收录到的声音送去 ChatGPT 那边 transcribe 出一个结果，然后根据返回字段做一层很基础的 filter：

1. 必须是中文（因为我爸妈纯说中文）
2. 结果不能为空

只有这两个 filter 都过了，才会去请求 OpenAI Realtime 2.1 Mini 模型生成 response，不然就不回答。这套过滤非常有效，请求次数降了很多，而且触发的内容确实都是有实质信息的。

但目前还有另一个问题没解决：从 Realtime 2.1 换成 Realtime 2.1 Mini 之后，虽然 prompt 完全没变，但在把输入图片也作为 input 的一部分时，好像 prompt 出了问题。我虽然改了一下，但问题依然没得到太大改善。现在的输出很多都在描述"我看到画面中有某某东西"，但我根本不需要它描述画面。可能是mini模型能力不足把传入图片理解成了需要去描述它。

这个问题之后肯定要解决，但我还不确定应该排在什么时候。我现在必须先把里面的整体架构搞清楚，把这件事的优先级提上来，否则之后再改，又容易变成写屎山代码。

另外一件事：因为电脑可能要关机，我让 Codex 帮我写了一份重启所有程序的脚本。其实像开机重启这类自动化支持是最基本的要求，之前是我自己没余力去搞，显得不太专业，但确实应该一开始就做好的
