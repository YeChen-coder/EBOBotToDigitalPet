这份 README 说实话不是什么正经的 technical README，更多是跟我之前的项目一样，纯吐槽、聊聊心路历程、讲讲怎么构思的以及踩了什么坑。

既然聊到这儿，就先说一个坑：
GitHub 上别人已经做过一个逆向开源项目(https://github.com/Playcolors-co/ha-enabot)， 但那是国际版的。如果你的账号 Region 是 China，就不能直接拿来用。这事得让你家的 Codex 去改， 两种region确实对应的授权和云的机制不一样。大家注意看一下手机 App 上显示的 Region 是什么，如果是 China 就不能直接套用那个开源项目。这和你注册时用的邮箱和密码默认归属地没关系，一切以手机 App 上显示的 Region 为准。 - 抱歉啊，这边确实有点讲得不太清楚。这个东西挺重要的，因为得从你手机上那个 App 里面获得两个挺关键的 key，然后这两个关键的 key 是去逆向出来的。它原本的那个 ha-enabot 项目是一个国际版的 App，然后作为一个 base。所以他那边好像默认的 region 是什么我给忘了，但是不重要，我就是说一下，他这个 region 在中国和非中国（在中国和什么其他区）是不一样的。虽然我也不知道他里边到底为什么不一样，但是他这个 region 必须得对了才行才能正常邮箱密码登录上，否则会报错，就这样。 

以及这个项目是搭在 Home Assistant 上的。对那些确实没用过 Home Assistant 的人（包括我自己也是第一次用），虽然之前搞了一堆逆向，但 Codex 这个狗东西也没告诉我有 Home Assistant 可以用。

跑题了，单纯说一下 Home Assistant：它是一个可以在 Docker 上运行的 platform。它做的事情就是作为一个中间层。我们各种 IoT 设备，不管是纯蓝牙还是带 Wi-Fi 的，都是最底层的终端设备。你想去控制它，又不想对每一个小设备、每一个日常电子小垃圾都从头 start from scratch，Home Assistant 这个中间层就很有必要了。它给用户提供了一个 unified 界面，不至于每调一个东西就要开一个程序。
反正 ChatGPT 跟我说 Home Assistant 能连纯蓝牙，但讲道理，前面我搞逆向的那些日常电子小垃圾，我还没放到 Home Assistant 上连过。这事先以后再说吧，那些设备目的都很单一、很 specific，其实用不着放到 unified 平台上来。最主要是现在懒得像条狗，而且我亲爱的 Codex 那个 5 小时的 usage limit 限制还没解，还得等着。

然后以及还有一件事，就是他那边如果要用到 Large Language Model 的能力，那就是得去填 API Key。OpenAI 那边的 API Key 必须得充钱。你要是账户上的 Credit 是个零，那他那个 API Key 你哪怕是现申请的，他也绝对会提示连接不上什么的，就这样. (以及再注意一下啊，它这个 credit 是会过期的。我之前充过，然后好久没用，现在一登上去看 credit 是个零，发现之前已经过期了)

遇到了很多现实制约(叹气)，我也想起来为什么去年夏天没有继续做 BeWithMe 这个项目了。最主要的原因就是整体的技术上限确实还没达到，现在的模型作为智能模型来说，其实并没有那么智能。

前面输入这部分，大概是把图像/视频再加上音频一起作为输入：

• 有些厉害的小伙伴愿意自己手搓一些 fusion 的方案，把音频和视频分开送给两个模型，中间做一些操作再出结果，比如很常见的 sensor fusion 这种做法。

• 但我个人确实懒，而且觉得作为个人搞出来的东西，连大厂的 Large Language Model 的一个脚趾头都干不过，何必白费这个力气。

用过 OpenAI 那边 ChatGPT 实时对话的都知道，人家已经做得非常好了。我完全没有竞争的想法和动力，既然人家做好了，直接站在巨人肩膀上用就行。我自己搞出来的效果估计差到不知道哪里去，而我是真想每天用这个东西，不是为了给简历凑项目，真搞出个垃圾来我自己都看不下去。

回到正题，OpenAI 那边能做到实时对话的（比如 Realtime API），拆开来看输入其实不能说是 realtime video，不然算力直接爆炸了。准确地说是连续的图像帧加上 audio：

1. Audio 这边确实是连续的
2. 图像这边跟其他以图像为输入的模型一样，基本上都是抽帧

不管是现实实现还是成本考虑，抽帧都是最实际的设计。我们又不需要像工业机器人那样按毫秒级来算，作为一个智能小助手，差不多就可以了。

回到正题接着谈：

如果这样的话，Home Assistant 那边现有的 LLM Vision 肯定是用不了了，因为那边绝对不支持将 Audio 作为输入。反正这种非常 Customized 的东西我早料到得自己手搓，只能自己写了，这个没办法。

再回头看，在目前还没有真正的 AGI 像神一样降临的阶段，基本上就确定用 ChatGPT Realtime 2.1 来作为 provider。

我们得考虑成本，毕竟 API 算钱我也肉疼：

1. 输出是按照 output token 计费的。
2. 输入的 context window 则是声音加上连续多帧图像。每次有输出或进行推理时，都会把当前收集到的这一串帧和听到的音频塞进 conversation 作为输入。

它那边的视频处理做得很好，会自动过滤掉 silent 状态下的视频，没有声音时不会自动触发推理。但它在图像帧作为输入时，确实没有判断「画面是否有变化」的机制，无法据此过滤是否要塞入 conversation，所以这块必须自己做。 -站在已经跑通了的后期，补充说明一下：ChatGPT 那边除了 Realtime 模型，其实还有一个 Chat Completions。Chat Completions 的逻辑是先做 transcribe，然后再把转写结果发 request 给它背后的模型。我之前其实想过要不要把 Realtime 改成 Chat Completions，但后来觉得还是不太行。我这边虽然也是先把一定时常的声音送去 transcribe，再根据返回的内容判断是否算有效输入，以此来决定要不要触发 request，但我送给 Realtime 模型那边的音频一直都是连着的，并不是一段一段、一卡一卡的。再加上我这边的场景确实是一个纯粹的 real-time 场景，而且我这边的“是否发request”判断和输入给realtime的audio是独立的没有关联的。所以综合考虑下来，我觉得还是得继续用 Realtime，Chat Completions 并不适合我目前的场景。

很多摄像头会把 motion detection 作为公开事件暴露出来，可以直接当作 trigger。但讲道理，EBO 这边并没有把 motion detection 作为公开事件暴露出来，所以这里还得自己写、额外加一层自己的逻辑。

目前 Codex 那边正在写着，看它最后能跑出个什么东西吧。啊，怎么说呢？我又感觉跟去年夏天一模一样了，又进到这个 pit hole，就不知道这次能出来个什么吧。人不能两次踏入相同的河流，却可以多次踏入同样的 pit hole。

又发现了一个问题：Realtime 2.1 那边有一个 60 分钟的强制限制。就是这么一个 session，不管里面是一直空白，还是说有音频输入，只要开了之后，时长一旦到了 60 分钟，它就不管里面空白地方占了多少，直接给切断。

这个限制让人很难受，对于一个 flowless 形式的体验不太好。

反正已经让 Codex 去找解决方案了，也不知道能给我搞出个啥。不过我觉得这种问题基本上都是天下英雄所见略同的，我肯定不是第一个撞上这个问题的人。我也没有什么心思非要成为一个解决该问题、踏着七彩祥云来的盖世英雄，前面比我聪明的人一大堆，直接用他们的解决办法就行。

要是 Codex 给我搞了一个非常扯的解决方案，那唯一的可能性就是单纯的运道不顺，没有碰到那个 "The One Right"

后续是他自己搞了一个 55 分钟的机制，分情况处理：如果这 55 分钟内全是空白，就直接新开一个 session；如果这 55 分钟内有内容，就总结一下，跟下面一起接着跑。

怎么说呢，可能人类开发者在很久之前就已经灭绝了吧，“老大，我们打不赢的”。Anyway，就先让它自己跑着去吧。等家里人回来的时候估计都在睡觉了，也不知道能跑成什么样。反正我电脑本来也是常年不关的，就看明天早上我爸妈给我打电话说什么吧，沉默是今晚的康桥。

有时候觉得，是不是有一些幻想会更好？假如不去谈 ChatGPT Model 和音视频输入的原理解析，如果什么都不知道，我可能真的会觉得对面有一个大脑在运转。不过科技发展到现在，真的已经很好了。

也许就到这儿吧？不对，科技还是再发展一下吧。毕竟真的想要赛博男友出现在身边，甚至都不用是机器人实体，哪怕只是一个电子眼陪着我、给我一些 motivation，就已经很好了。不知道在之后的 5 年还是 10 年能看到，我觉得最多 10 年吧。

世界上聪明人还是多的，总有一些老板、投资者或者个人开发者愿意在这个方向上做努力。不管底层的驱动力是什么，也谈不上是好事还是坏事，反正人类发展到这个阶段本来就会越来越孤独、越来越孤岛化。最主要的是，每个人都有选择使用什么产品的权利，自由还是挺重要的。

这也是我之前为什么觉得那个伴侣项目在心理上有点走不下去：因为它始终不是真人。虽然真人也许没那么好，我自己也是个没那么外向（E）的人，很多时候要产生真实的社交互动我甚至会有些抗拒，但我又很喜欢处于人群中的感觉。那得是真人的感觉，不能是纯 AI 或者纯机器人的那种。

人性本来就是很复杂的，考虑这些也没什么用，未来怎么发展也不是我这种小人物能决定的。从这个角度看，就是有什么用什么。

不唠叨了，反正让自己所处的环境越适合自己越好。

明天没抱着琴来，连口琴都没有。 

部署好家人那边提前回来了，说冒出了一段英文，熬夜熬穿了，听到问题更睡不着了，去查response， 狗东西不给prompt加上限制就中英文混合返回。

改了prompt, 能稳定中文了。 ./ebobot_catresponse.mp4 是家人拍摄的一段视频。 就是从说话人说话，到接收到返回，其实确实是有几秒的时延。但是这个东西毕竟得考虑到，它是建立在一个跨越了半个地球的网络前提下，所以首先是情有可原。其次，我觉得如果要缩短它的时延，估计得下大功夫了。

然后又发现它其实是不会自动记录的。我一开始以为 OpenAI API platform 的 usage 那边会有 log 所以一开始没有设定log的想法。之前用他们其他模型时确实能把这些 log 输出并显示出来，但这边并没有。当时我以为可能有时延，但过了两天，openai platform 上还是没有把对 Realtime API 的调用 log 放出来，我才意识到这东西可能就是没办法 log。

而且它一个 session 结束之后，就没办法把之前播放的内容拿回来了（它的返回是用语音返回的）。

另外它对输入其实也没有 log，所以我让 Codex 临时把输入的内容用chatgpt transcribe 做了记录，但这个记录其实又出现问题了。我这边先补充一下吧。

我让他记录日志（log）的时候，是每一次触发模型产生 response 的时候，去把输入的音频额外记录并翻译一下。

这是对输入记录的统计：
1. 空转写：144 条
2. 正确识别且有内容：54 条
3. 明确识别错误：24 条
   - 中文乱码、错词或无法理解（16 条）
   - 被错误识别成外文（8 条）
合计：144 + 54 + 24 = 222 条。

还是不太对。算了一下，他这边跟 API Platform 那边的 transcribe 请求是对得上的，一共 222 条。但是在 Responses and Chat Completions 那边只显示 122 条，这 122 条甚至还包括了我昨天测试期间产生的数据。所以这两天的真实使用情况，顶多也就触发了 100 次 Responses and Chat Completions，事情可能没有想的那么严重。

我说的“空”是指，它类似于一个 zero-shot 的场景：一开始没有人说话，也没有什么有效输入，用户在没有实质内容的情况下单纯问一句“你在吗？”，它肯定就会回“我在呀，我一直在陪伴你”这种没什么实质内容的话。但我不太喜欢这种回复，我想个办法把它改得更好一些。

因为这里有个逻辑：一般来说，用户要是有具体的事，就会直接跟陪伴助手说，比如问今天天气、查邮件等，这种情况其实不会遇到冷启动问题。但有些场景下用户可能只是单纯觉得 lonely，想找人说话，自己一时又想不出话题，所以才会问“你在不在”
所以这部分肯定得改。我不太确定光靠 Prompt 能不能解决，大概率是可以的。因为即使环境里发出了一些声音，它没从中获取到有效信息，这时候单纯搭话是没问题的；但我很介意它好几次直接说"没看到人"或者"人不在家"。

另外就是 noise reduction（降噪）设置，那个开了之后好了非常多，不至于说家里一有什么动静就莫名其妙把这个程序给唤醒了。现在父母那边反映说，它的干扰少了很多

现在的逻辑是：先把收录到的声音送去 ChatGPT 那边 transcribe 出一个结果，然后根据返回字段做一层很基础的 filter：

1. 必须是中文（因为我爸妈纯说中文）
2. 结果不能为空

只有这两个 filter 都过了，才会去请求 OpenAI Realtime 2.1 Mini 模型生成 response，不然就不回答。这套过滤非常有效，请求次数降了很多，而且触发的内容确实都是有实质信息的。

但目前还有另一个问题没解决：从 Realtime 2.1 换成 Realtime 2.1 Mini 之后，虽然 prompt 完全没变，但在把输入图片也作为 input 的一部分时，好像 prompt 出了问题。我虽然改了一下，但问题依然没得到太大改善。现在的输出很多都在描述"我看到画面中有某某东西"，但我根本不需要它描述画面。可能是mini模型能力不足把传入图片理解成了需要去描述它。

这个问题之后肯定要解决，但我还不确定应该排在什么时候。我现在必须先把里面的整体架构搞清楚，把这件事的优先级提上来，否则之后再改，又容易变成写屎山代码。

经验教训就是：凡是任何带参数的东西，在开发阶段请务必交代 Coding agent，让他把所有能改参数的东西全都暴露出来，不然的话之后真的是想用什么没什么呀. -补充，参数那边已经开了，只要是能有的参数全都暴露出来了。用不上是一回事，就先给他们个接口吧，不然的话每次实在是太折腾了，就为了这么一点事，这事不合算。
