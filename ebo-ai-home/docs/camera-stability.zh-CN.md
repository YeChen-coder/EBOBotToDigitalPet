# EBO 摄像头断流调查与稳定性修复

> **分支：`frigate`（Frigate 版，不是 main）。** 本分支的新架构当前针对本地，新版 AWS Dashboard 尚未完成迁移；完整的本地／云端＋Diagnostic Agent 版本在 [`main`](https://github.com/YeChen-coder/EBOBotToDigitalPet/tree/main)。[版本导航](../../VERSION-GUIDE.md)。

日期：2026-10-01，America/Toronto。代码和运行中的本地 Engine、assistant、Frigate、诊断 watcher / dashboard 已更新。

## 直接故障链

`frigate_camera_unavailable` 表示 Frigate 没有收到可用视频，不代表 Frigate 容器停止。实际日志确认：

1. 机器人 / Agora 解码源画面低帧率并间歇停止到达。
2. Engine 原来把这些不稳定的帧按固定 25fps 输入 FFmpeg，与实时 8kHz PCM 混流。输入节奏和声明的时间基准不一致，视频空窗还会阻塞音频混流。
3. MediaMTX 多次以 `i/o timeout` 关闭本机发布者，Engine FFmpeg 报 `Broken pipe`、退出码 224。
4. 读取端随之断开，Frigate 重试得到 `no one is publishing to path 'ebo'` / RTSP 404，摄像头帧率变为 0。

修复前的一份 Frigate 采样：`reconnects_last_hour=78`、`stalls_last_hour=111`、`camera_fps=0`、`connection_quality=unusable`。路径在发布者存活时正常，排除了单纯 RTSP 路径错误。

对照实验把真实输入限定为稳定 2fps：声明 25fps 时，45 秒内仅成功写入 202 个 50ms PCM 块；声明 2fps / 按实际时间打戳时分别为 857 / 898 个。稳定合成输入未复现实机超时，因此时间基准是已验证的放大因素，不能断言它是唯一根因。

另一项实机发现是启动竞态：RTC 的机器人加入回调先于 PCM observer 初始化，抛出 `AttributeError: 'Bridge' object has no attribute '_audio_obs'`，导致本次音频恢复任务没有启动。已修复首次连接和重新入会的注册顺序。

## 已实施的修复

- Engine 收帧回调只更新一个最新帧槽，不再在 SDK 回调内阻塞写入或重建编码器。独立 worker 按声明的帧率输出，丢弃积压旧帧。
- 短暂无新画面时维持上一帧的传输；PCM 独立按 20ms 时钟输出，缓存限制为 200ms，缺样填充静音。保帧和静音仅保持传输，不能证明机器人画面或麦克风健康。
- 写管道使用非阻塞写入和截止时间。编码器退出、管道卡住、MediaMTX 退出均由 worker 自动恢复，即使没有新源帧也能恢复。关闭时先终止并回收编码器，避免关闭 stdin 卡死。
- MediaMTX 日志保留发布者关闭原因；多机器人使用独立 RTP / RTCP 端口，禁用未使用且会争抢端口的 SRT 服务。
- 音视频观察器在 RTC 入会前注册，机器人立即加入时也能获得当前连接的 PCM observer；旧连接的恢复任务不能影响新连接。
- 已经开始过视频后再次断帧也会请求关键帧；每 2 秒检查，超过 3 秒无源帧开始轻量恢复，唤醒间隔至少 15 秒，失败记录 SDK 返回值。长期无源画面时沿用有间隔限制的 RTC 重建；媒体 watchdog 不再被 30 秒 token 检查节奏推迟。
- Engine 每 5 秒发布实际源视频健康和 Agora 视频统计。健康只由真正收到的解码帧更新，20 秒过期；关闭摄像头和断开连接分别呈现。
- assistant 同时检查 RTSP 传输和机器人真实音视频来源。源视频过期时不把保帧当新画面送给模型，也不凭保留的人脸事件加载家庭成员身份；音频可以继续工作。
- Frigate 仅订阅视频，assistant 音频读取器仅订阅音频；音频读取无数据 10 秒会退出并重连。自动唤醒不会覆盖明确关闭的摄像头开关。
- 诊断区分“Frigate 未收到摄像头视频”和“机器人源视频不可用”；源视频故障不触发盲目重启 assistant。Dashboard 增加实际摄像头源状态。

## 早期重连保护是否被改版覆盖

对照可查 Git 历史、修复前镜像 `before-camera-20261001` 和故障日志，结论是：原有视频重连保护仍在运行，主要问题是既有保护的覆盖和触发条件不足；另有后续音频恢复改动引入的启动竞态。

- 最早可查的 `d84d5cd`（2026-09-01 快照）已经包含 FFmpeg 退出后重启、`_force_rejoin` 和媒体 watchdog。该快照只能证明当时已有，不能确定更早的开发日期。
- `ebo_video.py` 在这份快照、修复前 HEAD 和修复前实际运行镜像中，统一换行符后的 SHA-256 完全一致。不能把这次视频模块缺口解释为后续改版删掉保护。
- 故障原日志实际记录 `09:28:56 ffmpeg exited (rc=224) — restarting encoder`，以及 `09:31:55 [watchdog] ... scheduling rejoin` / `forcing a fresh RTC rejoin`。重连确实发生，随后又发生发布超时。
- 原 FFmpeg 重建检查位于 `on_frame`：没有下一帧就不能由这条路径重建；管道阻塞写入没有截止时间。原轻量恢复仅检查 `video.frames == 0`，主要处理从未收到首帧，不能识别已有画面后的冻结。独立 RTC watchdog 虽然能兜底，但位于 30 秒检查门之后，并有启动宽限和 90 秒重建限速；这些保护没有解决低帧率音视频混流再次停顿的问题。这些代码结构在 9 月 1 日快照中已经存在。
- `9034cfa`（2026-09-16，音频源恢复修复）新增了机器人加入回调读取 `self._audio_obs`，而该 observer 当时在入会之后才注册。后续实机复核捕捉到了这条新支路的初始化竞态。这是可定位到后续改动的缺陷，影响音频恢复任务；没有证据证明它是本次视频发布超时的直接原因。

因此，早期的重连并非完全无效：它能把会话或编码器拉回来，但未保证回来之后持续可用。本次修复保留既有 RTC 重建，补上无新帧时的独立发布恢复、运行中冻结识别、混流时钟和阻塞截止时间，并修正新增音频恢复的注册顺序。

## 已知边界

这次修复消除了本地传输把断帧扩大为全链路崩溃的行为，并增加了恢复和真实来源验证。五分钟采样仍捕捉到一次上游画面冻结，不能承诺公网、机器人发布端或 Agora SDK 解码从此没有断帧。新增统计保留 SDK 原始数值，尚未确认量纲的字段不解释为百分比；目前证据不足以指定某台路由器或某个云中继为唯一原因。
